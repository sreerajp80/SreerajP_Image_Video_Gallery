# Plan — "Set as wallpaper" from the viewer

**Status:** completed

## 1. What the issue is

There is no way to use a photo as the phone's wallpaper from the app. The user has to leave the
app, open Android's wallpaper settings and find the photo again.

## 2. What will change (user view)

- In the photo viewer's ⋮ menu, a new item **"Set as wallpaper"** appears for photos (not videos).
- Tapping it opens **Android's own wallpaper screen** with that photo. There the user crops it and
  picks home screen, lock screen or both. The app itself never changes the wallpaper.
- If the phone's wallpaper screen refuses the photo, Android's **"Set as"** list opens instead
  (wallpaper apps, gallery apps, and on some phones the contact photo option).
- If neither can open, a short message says so. Nothing crashes.

The item is hidden when it cannot work:
- videos;
- items in the trash (other apps may not be able to read them);
- items whose address is not a MediaStore address (`content://media/…`). For example, a photo
  another app opened in this viewer.

## 3. Design (layers)

- **Rule (`lib/core/domain/viewer/wallpaper_rules.dart`):** a pure function
  `canSetAsWallpaper(MediaItem)`: image, not in the trash, and `uri` is a `content://media/` address.
  Pure rules live in `core/domain/` so the widget does not import a service (G46).
- **Kotlin (`IntentChannelHandler.kt`):** new method `setAsWallpaper(uri, mimeType)` on the existing
  intents channel, next to `shareFile`.
  1. Check again that the URI is `content://` with authority `media` (MediaStore). Anything else
     is refused with `bad_uri`, the same "check in Dart and again in Kotlin" rule the scanner uses.
  2. Try `WallpaperManager.getCropAndSetWallpaperIntent(uri)`, the system wallpaper screen, with a
     read grant for that one URI.
  3. If that throws (some phone makers do not support it), fall back to `Intent.ACTION_ATTACH_DATA`
     in a chooser titled with a localized "Set as" text.
  4. If no app can take it, return the `no_app` error.
- **Dart service (`lib/services/platform/wallpaper_service.dart`):** small wrapper, in the same style
  as `ShareService`. Returns `true` when Android's screen opened, `false` otherwise, and logs only
  the error type through `AppLogger` (no file names or paths).
- **Provider (`lib/providers/viewer_providers.dart`):** `wallpaperServiceProvider`.
- **Viewer:** `ViewerAppBar` gets a menu item and an `onSetAsWallpaper` callback.
  `MediaViewerScreen` calls the service and shows a SnackBar when it returns `false`.

**No new permission.** `android.permission.SET_WALLPAPER` is only needed when an app writes the
wallpaper itself. Here Android's own screen does that. No manifest change: an intent started
directly needs no `<queries>` entry.

## 6. How it will be checked

- `flutter gen-l10n`, `dart format .`, `flutter analyze` (zero issues), `flutter test`.
- Rule tests: photo yes; video, trashed item, non-MediaStore URI, missing URI no.
- Service tests: the right method and arguments are sent; `true` on success; `false` (no throw) on a
  `PlatformException` or a missing plugin.
- Widget test: the menu shows "Set as wallpaper" for a photo and not for a video, in `en`/`ml`/`sa`.
- A `flutter build apk --flavor dev --debug` to make sure the Kotlin compiles. Then
  `android\gradlew --stop` and a check for leftover Gradle/Kotlin daemons (global rule).
- **Owner, on a real phone (I cannot):** set a photo as wallpaper. Ideally also on a second brand
  of phone, because the wallpaper screen differs between makers.

## 7. Security impact

Touches the platform folder (Kotlin) and sends an outgoing intent. The only data leaving the app is
a **read grant for one MediaStore URI**, given to Android's wallpaper screen or to the app the user
picks in the "Set as" list. The URI is checked to be a MediaStore address in both Dart and Kotlin, so
the app's private files (vault, cache) can never be handed out this way. No new permission, no
manifest change, no network, no new dependency.

## 8. Risks and honest limits

- **Behaviour differs by phone maker.** Pixel phones show the system crop screen; some Samsung and
  Xiaomi versions throw on `getCropAndSetWallpaperIntent` and will show the "Set as" list instead.
  Both work, but they look different. I am fairly sure of this, not certain, because it varies by
  Android version.
- **Partial photo access (Android 14 "selected photos"):** a photo the user did not select is not
  in the app's list anyway, so it cannot reach this menu.
- Vault photos are not covered: they are encrypted and open in a different viewer. Supporting them
  would mean writing a decrypted copy to a shared place, which goes against the vault's purpose.
