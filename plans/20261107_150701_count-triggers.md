# Keep album and tag counts right with database triggers

**Status:** completed

## The issue

The `item_count` column on `albums` and `tags` counts every link, including photos that are in
the trash, in the vault, or out of reach (hidden by limited media access). Dart code saves it
only when a link is added or removed (`AlbumDao._refreshCount`, and three recounts in `TagDao`).
Moving a photo to the trash or vault, or a scan that hides it, changes what is visible without
touching the saved number, so it goes stale.

The screens are correct today, because every read swaps in a live count
(`AlbumDao._albumSelect`, `TagDao._tagSelect`). The saved number is wrong, and nothing reads it
yet, but it misleads anyone who trusts it later.

## The fix: let the database keep the number right

A trigger is a small rule stored inside SQLite. It runs on its own when a row changes, so no
Dart code can forget to call it. The rule for "visible" stays the one in
`DatabaseConstants.visibleMediaCondition` (not vaulted, not in trash, not out of reach).

Triggers (schema version 8):

| Trigger | Fires on | Does |
|---|---|---|
| `trg_album_count_link_insert` | insert into `album_media_entries` | recount that album |
| `trg_album_count_link_delete` | delete from `album_media_entries` (also foreign key cascades) | recount that album |
| `trg_tag_count_link_insert` | insert into `media_tag_entries` | recount that tag |
| `trg_tag_count_link_delete` | delete from `media_tag_entries` (also cascades) | recount that tag |
| `trg_count_media_visibility` | update of `is_vaulted`, `is_trash` or `is_out_of_reach` on `media_items`, only when visibility really changed | recount every album and tag that photo is in |
| `trg_album_count_guard` | insert into `albums`, or update of its `item_count` | set `item_count` to the true visible count |
| `trg_tag_count_guard` | insert into `tags`, or update of its `item_count` | set `item_count` to the true visible count |

The two guard triggers matter because `insertAlbum`, `updateAlbum`, `insertTag` and `updateTag`
write the whole row from the model (`toMap()`), which includes `item_count`. The guard corrects
whatever Dart sends, so the database alone owns this number. SQLite does not let a trigger fire
itself again by default (`recursive_triggers` is off), so the guard cannot loop.

Links are rarely updated in place (no code does it), so there is no update trigger on the two
link tables. Deleting a photo needs no trigger of its own: its links are removed by the foreign
key cascade, and the link delete triggers fire for that. The tests prove this.

### Speed

The visibility trigger looks up a photo's albums by `media_id`. `album_media_entries` has no
index on that column (its primary key starts with `album_id`), so a new index
`idx_album_media_media_id` is added. `media_tag_entries` already has one. Each recount is a small
indexed `COUNT`. A limited-access scan that hides many photos runs one recount per link, inside
the same transaction, which is fine for a phone gallery.

### What stays the same

- Screens keep reading the live count. Now both numbers agree, and switching reads to the saved
  column can be a separate, later change once this has proved itself.
- Smart albums (favourites, videos and so on) have no link rows, so their saved count stays 0,
  as it is today.
- Backups still leave the count out.

## How it will be checked

```bash
dart format .
flutter analyze
flutter test
```

The new tests read the raw `item_count` column straight from the table, not through the DAO,
because the DAO read hides it behind the live count.

## Security impact

Storage only: a local SQLite schema change (version 8) with new triggers and one index. No
permission, network, or file change. No media data leaves the device.

## Risks

- A migration that fails would stop the app opening the database. It only adds triggers and an
  index and runs `UPDATE`s, all with `IF NOT EXISTS`, and it is covered by the upgrade test.
- Logic that lives in SQL is harder to read than Dart. The trigger SQL is built from
  `DatabaseConstants` names, like the existing search triggers, and each one has a comment.
