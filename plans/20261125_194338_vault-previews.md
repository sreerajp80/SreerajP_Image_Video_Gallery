# Plan — Vault previews that actually get made (and a backfill for items without one)

**Status:** completed

## The issue

On the test phone (Android 10) on 2026-11-25, **no vault item got a preview**: not the 7.2 MB
photos, and not an 18 KB 800×600 photo either. Every tile shows a plain icon, and the owner's
real vault very likely has no previews at all.

**Cause.** `VaultPreviewService._imagePreview` decodes the photo from its **file path**
(`img.decodeImageFile(item.path)`), and `_videoPreview` hands the path to `grabFrame`. On
Android 10 this app runs under scoped storage (`LEGACY_STORAGE: ignore`), and an app cannot
read shared photos by file path there, only through a `content://` URI. That is the same rule
that broke Restore. The error is caught on purpose (a missing preview must not stop an
import), so it fails silently every time. I was wrong earlier when I blamed memory on big
photos: the small photo shows it is the path.

Two smaller points:

- The Dart decode runs on the UI isolate. A 12-megapixel decode in pure Dart can freeze the
  screen for seconds.
- `vaultThumbnailProvider` does not refresh after a batch, so a tile that once read "no
  preview" keeps showing the icon until the vault is reopened.

## The fix

### 1. New imports: previews through MediaStore

`VaultPreviewService.buildPreview(item)`:

- **When the item has a `content://` URI** (every gallery item does): call the existing
  `MediaStoreChannel.loadThumbnail(uri, 320, 320)`. This is the same call the gallery grid
  already uses. It works on Android 10+, covers photos and videos, applies the photo's
  rotation, and runs natively off the UI thread. The bytes stay in memory and go straight to
  the encryptor, as today.
- **Otherwise** (a file received in a phone move, staged in app-private storage, where path
  reads are allowed): today's decode, now inside `Isolate.run`, and today's `grabFrame` for
  video.

### 2. Backfill: previews for items already in the vault

New `VaultPreviewBackfillService` (services layer). After unlock, once the format upgrade has
finished, it makes a preview for each item that has none, one at a time, in the background:

- **Photos:** new Kotlin vault method `previewFromPayload`. It decrypts the payload into
  memory and decodes it with `BitmapFactory`, using `inSampleSize` so a 12 MP photo is never
  decoded at full size. It applies the EXIF rotation (framework `android.media.ExifInterface`,
  no new library), scales the longest side to 320, and returns JPEG bytes. No file is written.
  Payloads over the existing in-memory limit (64 MB) are skipped.
- **Videos:** the existing route used for playback. Decrypt to the app-private working file,
  `grabFrame`, then shred the working file at once.
- The preview is encrypted with `encryptThumbnailBytes`, **read back** (`verifyWritten`), and
  only then written to the row through `VaultDao.updateEncryption` (only the preview columns
  change).
- An item whose preview cannot be made is marked tried for this session (kept in memory) and
  not retried until the next unlock. It never fails anything: the item keeps its icon.
- It stops when the vault locks or a batch starts, as the format upgrade does.

### 3. Tiles refresh

`vaultThumbnailProvider` also watches `vaultRevisionProvider`, and the backfill bumps the
revision when it has added previews (once per run, not once per item). A batch bumps it
already.

## Security impact

Touches storage and crypto paths.

- Previews stay **memory-only** until encrypted, as today.
- The backfill decrypts a photo into memory: the same exposure as opening it in the viewer.
  For a video it uses the existing app-private working file, shredded straight after.
- **One honest note, unchanged by this plan:** Android's MediaStore keeps its own cached
  thumbnail of every gallery photo in its private storage. The gallery grid already made one
  for each photo before it was ever vaulted. It goes when the original's MediaStore entry is
  deleted (shredding the original does that); while the original is only hidden, it stays.
  This plan adds no new copy: `loadThumbnail` reuses Android's cache. It is written down in
  the security doc so it is not a surprise.
