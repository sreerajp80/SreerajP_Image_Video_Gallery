# Device Sync: app data by QR, photos and data by Wi-Fi

**Status:** completed

## 1. The issue

The owner wants one **Device Sync** entry in Settings. From there the user can copy this
app's contents to another phone running Drishya, in two ways:

- **QR:** app data only (tags, albums, favourites, notes, places). No photos.
- **Wi-Fi:** photos and videos, together with their app data.

The direction is **one-way and merge-only**. The sending phone gives and the receiving phone
only gains. Nothing is ever deleted or overwritten on either phone (hard rule 4). A two-way
sync, which would have to handle deletes and conflicts, is out of scope.

The owner's design for Wi-Fi:

- The user picks **folders or albums** to send, not "everything".
- One send has a **size limit**. The app warns when the selection is bigger.
- The app **marks what was sent**, so the rest can go in the next send.
- The app checks the **receiver's free space** first.
- Received photos go into **one fixed folder** on the receiver.

The plan also covers **photos that sit in different folders on the two phones**. That problem
affects backup restore, QR data sync and Wi-Fi sync in the same way.

### 1.1 What exists today (checked while planning)

| Piece | Where | State |
|---|---|---|
| QR pairing, encrypted Wi-Fi transfer | `lib/services/sync/` | Works. Carries files plus favourite, notes and tag names |
| Receive folder | `AppConstants.syncReceiveDirectoryName` | Images go to `Pictures/Gallery Transfers`, videos to `Movies/Gallery Transfers` |
| Duplicate skip | `ReceivedMediaService.alreadyHave` | Works only for files whose SHA-256 is already in the receiver's database |
| Backup archive and restore matching | `lib/services/backup/` | Matches by id → SHA-256 → path → name+size+date |
| Settings entry | `lib/screens/settings/settings_screen.dart` | None for sync. The Transfer screen is reached from the ⋮ menu and the selection bar |

### 1.2 Problems found in the current code

1. **The whole file is read into memory to hash it.**
   `TransferSessionService.buildManifest` calls `file.readAsBytes()`. The file limit is
   4 GB, so a large video can run the app out of memory and crash it (breaks hard rule 5).
2. **The limit of 2,000 files cuts the list silently.** `items.take(syncMaxManifestEntries)`
   drops the rest and does not tell the user.
3. **Hashes are thrown away.**
   - The sender computes a SHA-256 for every file it sends, but does not save it.
   - The receiver checks the digest of every file it receives, but does not save it either.
   - So the "already have it" check misses files it could have caught.
4. **Albums and places do not travel over Wi-Fi.** Only tags, notes and favourite do.
5. **A folder holding both photos and videos lands in two places.** Images go to
   `Pictures/...` and videos to `Movies/...`. The gallery then shows two folders with the
   same name.

### 1.3 Photos in different folders on the two devices

Folders differ between phones, and the app cannot create another app's folder
(for example WhatsApp's) on the receiver. The plan handles this in three ways:

- **App data never depends on folders.** QR sync and backup restore find "the same photo" by
  content (SHA-256), or by name + size + date taken. The folder does not matter.
- **Received files keep their folder name, inside one folder the app owns.**
  `Camera` on the sender becomes `Pictures/Drishya Sync/Camera/` on the receiver.
  `WhatsApp Images` becomes `Pictures/Drishya Sync/WhatsApp Images/`. Videos go into the same
  folder as the photos (Android allows videos under `Pictures/`), so one sender folder stays
  one receiver folder.
- **Stronger matching** (fixes a weak spot in today's restore). Today a photo with no saved
  SHA-256 and with a different date on the other phone (screenshots and downloads often have
  no EXIF date) is not matched, and its tags are lost without any notice. The fix:
  - The sender computes the missing SHA-256 values before it writes the data, for photos that
    have app data only.
  - The receiver hashes only the local files whose **size** equals the size of an unmatched
    record. This narrows thousands of files down to a few.
  - **Known limit, kept on purpose:** a copy that was compressed again (for example sent
    through a chat app) is a different file and is not matched. A "looks similar" match
    could put tags on the wrong photo, so this plan does not guess. The preview already
    reports these photos as "not found on this device".

## 2. The design

### 2.1 Settings → Device Sync screen

- **Settings:** a new "Device Sync" entry, next to "Backup and restore".
- **Device Sync screen:** shows three cards:
  1. **Send app data by QR**
  2. **Send photos and data by Wi-Fi**
  3. **Receive** (works for both QR and Wi-Fi)
- **Existing entry points stay:** the ⋮ menu item and the selection bar "Send to a device"
  open the Wi-Fi flow as they do today.

### 2.2 QR: app data only

**The data**
- It is the same content as a backup archive: tags, albums, favourites, notes, places, plus
  the identity of each photo (name, size, date, SHA-256).
- It is **not the database file**. That file holds this phone's own ids, paths and indexes,
  which are wrong on another phone, and it is too big for QR.
- Only photos with app data are included.

**The steps**
1. The receiver opens Receive → QR. It shows a **key QR**: a one-time random key, short.
2. The sender scans it. This is the same steps as Wi-Fi pairing (receiver shows, sender
   scans), using the existing scanner and QR widgets.
3. The sender compresses the data (gzip), then encrypts it with that key (AES-GCM, through
   the existing `crypto` package or backup crypto). It splits the result into frames of
   about 800 bytes.
4. The sender plays the frames as an **animated QR** that loops.
5. The receiver collects the frames in any order and shows "34 of 52". It finishes when it
   has all of them.

**Each frame** carries a small header: format version, session id, frame number, frame
count, and a checksum.

**Size check before showing anything**
- The sender works out the frame count first.
- Over a cap (about 100 frames), it says "too much for QR, use Wi-Fi" and shows no codes.

**On the receiver**
- The data goes into the **existing restore preview and apply**: `BackupMergeService` →
  `RestorePreviewSheet` → `BackupApplyService`.
- So the user sees the counts and says yes first. As with restore, the receiver only gains:
  nothing is removed and no existing note is blanked.

**Network:** QR sync opens no network connection at all.

### 2.3 Wi-Fi: photos and data

**New steps**
1. **Pair first** (same QR or typed code as today).
2. On connect, both phones send a short **hello**. It holds the phone's own **install id**
   and name. The receiver also sends its **free space**.
3. The sender opens the **picker**, which lists device folders and albums. Each row shows:
   item count, total size, and **"Sent 320 of 1,200 to Pixel 7"** for the paired phone.
4. The user picks folders and albums.
5. The app works out what to send:
   - the picked photos,
   - minus the ones already marked as sent to this phone,
   - with the total size added up.
6. **Limit per send:** the smaller of a fixed cap (5 GB, a constant we can tune) and the
   receiver's free space minus a 5% margin. Also at most 2,000 files.
7. **If the selection is bigger:** a warning says "This send will carry 4.8 GB of 12.3 GB.
   The rest can go in the next send." The app takes whole folders in order, then whole
   files, up to the limit. The user can go ahead or change the selection.
8. Files are sent. Each file that lands is **marked as sent to that phone**, and so is each
   file the receiver says it already has.
9. **At the end:** "Sent 1,180 files. 2,140 left. Send the rest" (one tap, same peer, same
   selection).

**What travels with each file**
- Already today: favourite, notes, tag names.
- New: **album names** and **place** (address, latitude, longitude).
- New: the **source folder name**, used for the subfolder on the receiver.

The receiver finds or creates tags and albums by name, as restore already does.

**Marks**
- A new database table: which media, sent to which install id, its SHA-256, and when.
- **The marks decide what is offered.** The receiver's SHA-256 check still decides what
  really moves. If the other phone was reset or a photo was edited later, its SHA-256 no
  longer matches the mark, so the file is offered again.

**Install id**
- A random id, created once on first use and saved in plain app preferences.
- It is not a hardware id and is not secret. It is only sent inside the encrypted session,
  to a phone the user paired with by hand.

**Free space**
- The receiver reads its free space with Android's `StatFs`, through the existing MediaStore
  channel. This needs no permission.
- Checked again before each file. If space runs out, the send stops cleanly. Files already
  sent stay marked.

**Interruptions**
- The screen is kept on while a send runs, with the window flag already used by video
  playback.
- If the send stops anyway, every file that landed is already marked, so "Send the rest"
  carries on from where it stopped.

**Protocol version goes up by one.** An older build is refused with the existing "update the
app on both phones" message. That is acceptable before the first release that includes this.

### 2.4 Fixes from §1.2

1. Hash files **in pieces** (streamed), never the whole file at once.
2. Never cut the list silently. The limits in §2.3 are shown to the user.
3. **Save the hashes:**
   - Sender: the SHA-256 it computes goes into its database (`MediaDao.updateHashes`), so the
     next send skips that work.
   - Receiver: the checked SHA-256 is saved on the new row.
4. Albums and places travel (§2.3).
5. One receiver folder per sender folder (§1.3).

## 4. Order of work

Each phase ends with `dart format .`, `flutter analyze` and `flutter test` all clean.

1. **Safety fixes:** streamed hashing, save hashes on both sides, no silent cut. This is
   small, and it fixes a real crash risk on its own.
2. **Folder layout and data that travels:** the `Drishya Sync/<folder>` layout, albums and
   places over Wi-Fi.
3. **Stronger restore matching** (§1.3).
4. **Database and marks:** schema 9, install id, hello with free space.
5. **Wi-Fi picker and limits:** folder/album picker, limit warning, "Send the rest", keep screen on.
6. **QR data sync:** codec, send and receive screens, hand-off to restore preview.
7. **Settings entry, Device Sync screen, text in all three languages, docs.**

## 5. How it will be checked

- **Automatic:** `dart format .`, `flutter analyze` (zero issues), `flutter test` (all pass).
- **On two real phones (owner):**
  - QR data sync of a small library.
  - Wi-Fi send of one folder that has both photos and videos. Check it lands as one folder.
  - A send bigger than the limit, then "Send the rest".
  - Turn Wi-Fi off half way, then resume.
  - A receiver with little free space.
  - A 1 GB+ video, to check no out-of-memory crash.
- **Text:** new Sanskrit strings flagged for the owner's review, as for G9.

## 6. Security impact

- **Network:** the local transfer protocol gets one new frame type, the hello. It carries
  the install id, device name, free space and source folder names.
  - It stays inside the existing encrypted, paired, private-address-only session.
  - `LocalAddressRules` is unchanged. No new socket, listener or remote host.
- **Untrusted input:** folder names, album names, tag names and the QR frames all come from
  another device.
  - Folder names are cleaned in Dart and again in Kotlin.
  - QR frames are size-capped, checksummed, and must decrypt and authenticate before use.
- **Storage:**
  - One new table, `sync_marks`.
  - One new preference, the install id. It is random, not a hardware id, and not secret.
  - Files are still written only through MediaStore, under the app's own `Pictures/Drishya
    Sync/` folder.
  - Nothing is overwritten or deleted.
- **Permissions:** none added. The camera is already declared for the pairing scan. Free
  space needs no permission.
- **Dependencies:** none added. It uses `qr_flutter`, `camera` + ZXing, `crypto` and
  `dart:io` gzip, which are all already present.
- **Privacy of QR data:** notes and places are encrypted with a one-time key. A person
  filming the animated codes cannot read them without also capturing the key QR.

2. **Receive folder name:** `Drishya Sync` replaces `Gallery Transfers`. Files received
