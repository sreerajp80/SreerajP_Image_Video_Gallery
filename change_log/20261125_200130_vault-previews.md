# Change log — Vault previews that actually get made (and a backfill)

Implements: [plans/20261125_194338_vault-previews.md](../plans/20261125_194338_vault-previews.md)

## What changed

### Kotlin (`VaultChannelHandler.kt`)

New `previewFromPayload`:
- decrypts a photo payload into memory (refused over the 64 MB in-memory limit);
- reads the bounds, then decodes with `inSampleSize`, so a 12 MP photo is never held at full
  size;
- applies the EXIF rotation (framework `android.media.ExifInterface`, no new library);
- scales the longest side to 320 and returns a JPEG (quality 80);
- wipes the decrypted buffer before returning;
- returns an empty array, never an error, when the bytes are not a decodable picture.

### Dart

- `vault_preview_service.dart`:
  - An item with a `content://` URI gets its preview from `MediaStoreChannel.loadThumbnail`
    (the call the gallery grid uses; photos and videos; rotation applied; native, off the UI
    thread). This replaces the path decode that Android 10 refuses.
  - Without a URI, or when Android has no thumbnail, it falls back to the old route. The
    photo decode now runs in `Isolate.run` (`decodeAndShrink`).
- **New** `vault_preview_backfill_service.dart`. After unlock and after the format upgrade, it
  makes previews one at a time for items with none:
  - photos through `previewFromPayload`;
  - videos through the app-private working file and `grabFrame`, the file shredded at once.

  Each preview is encrypted, read back (`verifyWritten`), and recorded through
  `updateEncryption`. A failure leaves the item as it was. A preview file left from before
  schema 2 (no IV) is deleted after the new one is recorded. The run stops on lock or when a
  batch starts.
- `vault_channel.dart` and `vault_crypto_service.dart`: `previewFromPayload()`.
- `vault_dao.dart`: `getIdsWithoutPreview()`. A preview with no IV counts as none.
- `vault_providers.dart`:
  - the preview service gets the MediaStore channel;
  - new `vaultPreviewBackfillServiceProvider`;
  - the lock controller runs the upgrade, then the backfill, and reloads once if either
    changed anything;
  - batches wait for both;
  - `vaultThumbnailProvider` also watches the revision, so tiles pick up new previews.

### Tests

- **New** `vault_preview_service_test.dart` (5 tests):
  - a gallery photo and a gallery video use MediaStore by URI and never read the path;
  - no MediaStore thumbnail falls back to the path route;
  - a staged file is decoded from its path and shrunk;
  - a failure gives null.
- **New** `vault_preview_backfill_service_test.dart` (7 tests):
  - a photo gets its preview from the payload, read back first, and its notes are kept;
  - a video goes through a working file that is shredded;
  - items that have a preview are left alone;
  - an undecodable picture keeps its icon;
  - a bad read-back records and leaves nothing;
  - the run stops when told;
  - a second call during a run returns at once.
- DAO: `getIdsWithoutPreview`. Lock controller: the backfill runs after the upgrade and
  causes one reload.

### Phone test (2026-11-25)

Dev build on the test phone (Android 10). Commands were sent to it by serial; other phones
were connected and were not touched.

1. With the **previous** build installed, moved an 18 KB test photo and a 4.6 KB test video
   into the vault. The video was recorded on the phone with `screenrecord` of the secure vault
   screen, so its frames are black. **No `.thm` was made for either**, which is the bug and
   the state of the owner's real vault.
2. Installed the new build and unlocked. Within seconds the **backfill added both previews**
   (3,676 B for the photo, 1,800 B for the video frame). No working file was left.
3. Moved a 7.2 MB photo in with the new build. **Its preview was made at import** (42,868 B).
4. Deleted the three items for good. The message read "3 items deleted for good" (the new
   string), and all payloads and previews were gone. Test originals were removed through
   MediaStore, folders deleted, and Gradle daemons stopped.

**Not checked by eye:** what the previews look like. The vault screen blocks screenshots
(`FLAG_SECURE`), so only the files were checked. The owner should open the vault on a phone
once to see the tiles.

## Security impact

- Previews stay memory-only until encrypted.
- The backfill decrypts a photo in memory (the same exposure as opening it in the viewer) and a
  video into the existing app-private working file, shredded at once.
- `loadThumbnail` reuses Android's own thumbnail cache. The vault adds no copy, and the note
  about Android's cache is now in the security doc.
- No new permission, package, string or database change.
