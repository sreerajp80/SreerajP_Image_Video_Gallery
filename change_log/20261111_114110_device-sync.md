# Change log: Device Sync (QR app data, Wi-Fi photos and data)

Implements [plans/20261111_110538_device-sync.md](../plans/20261111_110538_device-sync.md).

## What changed, and why

### Phase 1: safety fixes in the Wi-Fi transfer

- **Hashing in pieces.** The sender read each whole file into memory to hash it
  (`file.readAsBytes()`). The receiver also kept every received byte in a `List<int>` to hash at
  the end. A large video could use many gigabytes of memory on either side and crash the app.
  Both now hash in pieces (`TransferCryptoService.fileDigest`, `StreamingSha256`).
- **Hashes are kept.** The sender saves each SHA-256 it computes (`MediaDao.updateHashes`). The
  receiver saves the checked SHA-256 on the new row. The "already have it" check now catches more
  files.
- **No silent cut.** The 2,000-file limit is now applied and shown by the send picker (phase 5),
  not dropped silently.

### Phase 2: folders, and data that travels

- Received files go to `Pictures/Drishya Sync/<sender folder>` (`FolderNameRules`). Videos go
  under Pictures too (`underPictures`), so a sender folder with photos and videos stays one
  folder.
- Each file now also carries its album names, place (address, latitude, longitude) and source
  folder name.
- **Bug found and fixed:** the receiver applied favourite, notes and tags straight after copying
  the file, before the scan had given it a database row. The lookup found nothing, so these
  details were lost. They are now applied after the scan (`ReceivedMediaService.indexReceived`).
- **Privacy exports unchanged:** privacy-cleaned copies used the same default folder. They now
  name their old folder (`Gallery Transfers`) on purpose, so they do not move.

### Phase 3: stronger restore matching

- `DigestFillService` gives a SHA-256 to the photos a backup or QR send carries
  (`BackupCollectorService.collectFingerprinted`).
- During a restore, records nothing matched get a second pass: local photos of the same size are
  fingerprinted and matched again (`RestoreService.openPayload`).
- A copy that was compressed again is still not matched, on purpose.

### Phase 4: database, install id, peer info

- **Schema 8 → 9:** new `sync_marks` table, deleted with its media row.
- **Install id:** a random id per install (`DeviceIdentityService`). It is not a hardware id.
- **Protocol 2:** new frames `ping` (heartbeat every 15 s), `peerInfo` (install id, plus the
  receiver's free space) and `bye`. The idle clock now counts only what arrives. One pairing can
  carry several sends.
- **Free space:** the receiver checks it before each file (`hasRoomFor`). When it is full it
  reads past the file without keeping it and answers `noSpace`, and the sender stops.

### Phase 5: Wi-Fi picker, limits, "Send the rest"

- After pairing, the sender ticks folders and albums (`SendPickerView`).
- **Limits:** the smaller of 5 GB and the receiver's free space minus a reserve, and at most
  2,000 files (`SendLimitRules`, `SyncSelectionRules`). Order is kept. Files already sent to that
  phone are left out and counted.
- After each send, the same ticks are kept and **Send the rest** sends what is left. **Finish**
  ends the pairing.
- The screen stays on while a transfer is live.
- The Send card no longer needs a selection first.

### Phase 6: QR data sync (no network)

- The receiver shows a one-time key QR. The sender scans it, then gzips and encrypts the backup
  payload (AES-GCM, with the session id as associated data). It plays the result as a loop of QR
  codes, 400 bytes each, at most 150 (`QrFrameCodec`, `QrDataSyncService`).
- The receiver reads the codes in any order (`QrFrameCollector`), then shows the normal restore
  preview before anything is written.

### Phase 7: Settings, text, docs

- **Settings › Device Sync** (`DeviceSyncScreen`) with four cards: QR send, Wi-Fi send, QR
  receive, Wi-Fi receive.
- 46 new text keys in English, Malayalam and Sanskrit. One now-unused key
  (`bodySyncNothingSelected`) was removed.
- `docs/security.md` §19 updated, with new §19.6 and §19.7. `docs/architecture.md` updated
  (schema 9, routes, Device Sync section). `docs/known_gaps.md` gains G51 (Sanskrit review) and
  G52 (two-phone checks).

## Security impact

- **Network:** no new socket, listener or host. Three new frame types travel inside the existing
  encrypted session. `LocalAddressRules` is unchanged.
- **Untrusted input:** these are cleaned before use:
  - folder names (in Dart and again in Kotlin);
  - the install id (`PeerInfo.fromJson`);
  - latitude and longitude (must be finite);
  - QR frames (size cap, check value, then AES-GCM).
- **Storage:** one new table and one new plain preference (a random id, not secret). Files are
  still written only through MediaStore. Nothing is overwritten or deleted.
- **Permissions and dependencies:** none added.
