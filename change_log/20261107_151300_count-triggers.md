# Change log — album and tag counts kept right by database triggers

Implements [plans/20261107_150701_count-triggers.md](../plans/20261107_150701_count-triggers.md).

## What changed and why

The saved `item_count` on `albums` and `tags` counted photos in the trash, in the vault and out
of reach. It also went stale when a photo's visibility changed, because only Dart code that
added or removed a link recounted. Now the database itself keeps the number right, with
triggers, so no code path can forget to recount.

- **Schema 8** (`lib/repositories/database/database_constants.dart`).
- **`DatabaseHelper._createCountTriggers`** (`lib/repositories/database/database_helper.dart`)
  creates, on a new database and on upgrade:
  - index `idx_album_media_media_id`, so a photo's albums can be found by media id;
  - `trg_album_count_link_insert` / `_delete` and `trg_tag_count_link_insert` / `_delete`:
    recount when a link is added or removed, including removals by a foreign key cascade;
  - `trg_count_media_visibility`: recounts every album and tag of a photo when its
    `is_vaulted`, `is_trash` or `is_out_of_reach` change makes it visible or hidden;
  - `trg_album_count_guard_insert` / `_update` and `trg_tag_count_guard_insert` / `_update`:
    put the true count back when Dart writes a wrong one (whole-row writes from `toMap()`).
- **Upgrade to v8** creates the triggers and recounts every album and tag once
  (`_recountAllAlbumsAndTags`).
- **`AlbumDao`**: `_refreshCount` became `_touchAlbum`, which only stamps `date_modified`.
- **`TagDao`**: removed the Dart recounts in `addTagToMedia`, `removeTagFromMedia` and
  `setTagsForMedia`, and the unused `recountTag` / `_recountTagIn`. The two single-statement
  writes no longer need a transaction.
- Doc comments on the live-count reads now say the saved column holds the same number.
- `docs/architecture.md`: schema version 8, a migration table row, and the "Album and tag
  counts" note rewritten.

### Small difference from the plan

The plan listed one guard trigger each for albums and tags. A SQLite trigger fires on one kind
of event only, so each guard is two triggers (one for insert, one for update): nine triggers and
one index in total.

Screens still read the live count, as planned. Smart albums have no link rows, so their saved
count stays 0, as before.
